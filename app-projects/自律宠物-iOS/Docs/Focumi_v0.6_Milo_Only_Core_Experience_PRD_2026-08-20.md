## 1. Overview

Focumi 是一款以宠物陪伴为情绪入口、以专注计时和 iOS 干扰 App 限制为实用核心的 iPhone App。v0.6 本轮不重写现有 Session、Timer、Family Controls、Shield、Return、Live Activity 或持久化架构，只收口用户可见体验：采用已确认的暖米白、墨绿色、简洁手绘 UI；当前版本仅开发官方角色 Milo；保留伙伴选择能力，但在产品界面中隐藏 Max；新增约 1–2 秒、可提前结束且支持 Reduce Motion 的 Milo 品牌开场；完成“选择伙伴 → 设置任务 → 专注 → 返回 → 完成 → 记录”的核心闭环。

## 2. Problem

### 2.1 用户问题

目标用户在学习或工作时容易打开社交或娱乐 App，普通倒计时工具缺少情绪连接，难以形成“愿意再次回来”的日常使用感。

### 2.2 当前产品问题

1. 现有功能底座已覆盖专注、必要使用、返回和完成，但页面视觉不统一，角色与功能层级没有稳定闭环。
2. 外部 AI 生成图曾改变 Milo/Max 身份；视觉参考与官方角色资产没有严格分离。
3. 同时呈现多个角色扩大了资产、状态和验收范围；当前 Max 体验未闭环。
4. App 打开后直接进入功能页，缺少短暂、可识别但不拖慢用户的品牌进入时刻。

### 2.3 证据边界

- 已知：当前仓库存在本地 SwiftUI 核心流程、专注 reducer、系统能力适配代码及 Milo 官方状态资产。
- 已知：用户已暂定六页 UI 方向，并明确本轮只开发 Milo、隐藏 Max。
- 未知：陌生用户是否愿意安装、完成首次专注、自然复用或付费。
- 本 PRD 不把概念图、构建、模拟器或旧 TestFlight 状态视为需求成立或商业绿灯。

## 3. Product promise

> 和 Milo 一起，安静地完成眼前这一件事。

核心结果：用户能快速设定一个目标和时长，在 Milo 的陪伴下进入专注；离开后能无责备地返回；完成后获得清晰、克制的共同完成反馈。

## 4. Target users and situations

### 4.1 首批目标用户

- 容易在学习、阅读、写作或办公时被手机干扰的人。
- 喜欢温暖手绘宠物，但不希望 App 变成复杂养成游戏的人。
- 需要一次 15–120 分钟专注，而非医疗或成瘾治疗的人。

### 4.2 主要触发场景

- 准备完成一章阅读、一组习题、一段写作或一项桌面工作。
- 专注期间误入或主动打开干扰 App，之后返回当前目标。
- 完成一次专注后查看近期记录，并决定是否再次开始。

## 5. Goals and non-goals

### 5.1 Goals

1. 六个核心页面形成同一套清晰、温暖、宠物优先的视觉系统。
2. 当前所有正式用户表面只出现官方 Milo，不出现 Max 或其他宠物。
3. 保留未来伙伴选择扩展能力，不改变现有 `.cat` / `.dog` 兼容数据格式。
4. UI 改造不改变既有核心业务 reducer、系统能力语义和真实状态边界。
5. 启动时提供短、可提前结束、不会掩盖真实加载失败的 Milo 品牌过渡；只编排现有静态资产，不生产新角色动画资产。
6. 主路径支持 Dynamic Type、VoiceOver、Reduce Motion 和至少 44pt 触控区。
7. 建立可测试的首次专注、完成和返回事件，为后续 C/R 验证保留证据入口。

### 5.2 Non-goals

- Max 的页面、动画、状态补全或上线展示。
- 第三只宠物、宠物库、商城、抽卡、金币、XP、家具或复杂养成。
- 登录、账号、后端、云同步、社交、排行榜或订阅。
- 重新设计、重画或 AI 仿画 Milo。
- 重写 Session、Timer、Family Controls、Shield、Return、Live Activity 或持久化架构。
- Dark Mode；本轮只完成 Light Mode。
- TestFlight、App Store、公开招募或商业发布。

## 6. Product principles

1. **Milo first**：第一视觉焦点是官方 Milo；角色不能被当作卡片小图标。
2. **Clarity before decoration**：目标、计时器、真实状态和主操作优先于装饰。
3. **One screen, one primary action**：每页最多一个主 CTA；结束操作单独使用柔和橙色。
4. **No false system claims**：动画结束不代表 Shield 已生效、已解除或已恢复。
5. **No forced waiting**：品牌动画不能人为拖慢已经可用的 App。
6. **Official assets only**：运行时直接使用 Approved Milo 资产，不使用概念图中的生成角色。

### 6.1 v0.6 角色动效资产门禁

- v0.6 不生产新的 Milo 动画资产、逐帧帧列、spritesheet 或补间角色姿态。
- 正式体验仅使用现有 Approved Milo 静态姿态。
- 允许的增强方式仅包括：页面转场、现有静态姿态之间的状态切换、克制的 UI opacity/offset 过渡、Haptic 和可关闭的短声音。
- 不允许为了制造“生命感”对 Milo 静态图进行身体局部变形、骨骼绑定、AI 补帧或重新绘制。
- 角色逐帧动画属于后续体验增强，不是 v0.6 的实现范围、发布条件或发布阻断项。
- 后续若重启逐帧动画，须另立资产生产、身份一致性、性能、Reduce Motion 和真机验收门禁。

## 7. Scope: core surfaces

### 7.1 Launch moment（新增）

目的：建立品牌识别，并自然进入主流程。

- 使用系统 Launch Screen 提供即时静态底色，禁止在系统启动阶段执行自定义长动画。
- App UI 可交互后显示约 1–2 秒的轻量品牌过渡。
- 建议顺序：米白背景 → 爪印淡入/轻移 → 现有 `milo_idle_v1` 整体淡入或轻移 → `Focumi` 淡入 → 进入目标页面。
- 不制作眨眼、探头等新角色帧；Milo 本体保持 Approved 静态图完整，不做局部形变。
- 内容准备完成后允许提前收束，不设置固定最低等待时间。
- Reduce Motion 开启时使用静态 Milo + Focumi，短淡入后进入。
- 冷启动可显示；同一进程内前后台切换不重复播放。
- 动画不可读写业务状态，不可阻塞恢复页、权限页或错误页。

### 7.2 伙伴选择

目的：保留伙伴认领入口，同时将当前正式角色锁定为 Milo。

- 页面只展示官方 `milo_idle_v1`。
- Max 和其他伙伴不显示，不展示灰锁卡、剪影或“即将上线”占位。
- 保留现有伙伴选择的数据与路由边界；不得删除 `.dog` 兼容标识或迁移旧数据。
- 新用户点击“选择 Milo”后进入任务设置，并持久化选择结果。
- 已有用户若历史值为 Max/`.dog`：本轮需先确定兼容策略，未确认前不得静默覆盖数据。

### 7.3 任务设置

目的：让用户在最少步骤中明确一件事并开始专注。

- 展示官方 Milo Focus/Pact 相关资产。
- 用户可输入一个任务目标。
- 用户可选择既有合法专注时长。
- 现有 Family Controls 权限、App 选择和缺失条件必须继续真实呈现。
- 主按钮为深绿色胶囊“开始专注”，条件不足时说明缺少什么。

### 7.4 专注计时

目的：让 Milo、目标和剩余时间成为三个清晰锚点。

- 使用官方 `milo_focus_v2`。
- 显示目标、倒计时和必要的真实保护措辞。
- “暂停/必要使用”行为必须沿用现有业务定义，不因概念图新增不存在的 reducer 状态。
- “结束专注”使用柔和橙色，并保留真实结束确认。
- 动画、角色点击反馈和计时显示不得成为 deadline 真值。

### 7.5 返回专注

目的：用户离开后，Milo 无责备地欢迎用户回来并恢复当前目标。

- 使用官方静态 `milo_return_v1`；本轮不生产或接入新的 Return 逐帧资产。
- 显示离开时长、当前目标和真实恢复状态。
- 主按钮为“继续专注”。
- “正在请求恢复保护”与“系统已恢复”必须分开；本地命令回执不能包装成系统成功。

### 7.6 完成庆祝

目的：以低信息密度提供共同完成感。

- 只使用官方 `milo_complete_v1`，不出现 Max。
- 显示完成标题、本次目标和实际专注时长。
- 不加入金币、等级、奖章货币、烟花或复杂奖励系统。
- 主按钮根据现有流程使用“完成”或“再次一起专注”；最终文案待用户确认。

### 7.7 专注记录

目的：让用户看到真实完成，而不是建立复杂数据仪表盘。

- 使用官方 Milo 静态资产；若没有正式睡眠姿态，不得用 AI 重画睡眠 Milo。
- 展示已有数据能够真实支持的今日专注、完成次数、连续天数或近期记录。
- 不为匹配概念图虚构数据字段。
- 是否提供“查看详情”按钮取决于是否存在真实详情页；没有目的地则不显示。

## 8. Functional requirements

| ID | Requirement | Acceptance |
| --- | --- | --- |
| FR-01 | 新安装用户可看到伙伴选择页，并只看到 Milo | 页面无 Max 文案、图片、可访问性节点和占位 |
| FR-02 | 用户可选择 Milo 并进入任务设置 | 选择结果沿用现有 Store 持久化，重启后保持 |
| FR-03 | 现有 Max 数据不会被静默破坏 | 升级策略经用户确认并有测试；未确认前停止迁移 |
| FR-04 | 用户可输入目标并选择合法时长 | 无目标或必要条件不足时不能误开始，并给出明确提示 |
| FR-05 | 用户可开始一次专注并看到真实倒计时 | deadline 仍由现有 reducer/store 管理，UI 不另建计时真值 |
| FR-06 | 用户可结束当前专注 | 保留确认步骤；结束后执行现有清理流程 |
| FR-07 | 用户离开后可返回当前目标 | 返回 UI 不丢目标；恢复保护状态使用诚实措辞 |
| FR-08 | deadline 到达后显示 Milo 完成页 | 完成只结算一次，重复激活不重复奖励或记录 |
| FR-09 | 用户可查看现有数据支持的专注记录 | 页面数据与 Store 一致，不展示伪造统计 |
| FR-10 | 冷启动显示短 Milo 品牌过渡 | 不强制等待；前后台切换不重复播放 |
| FR-11 | 所有正式页面只引用 Approved Milo 资产 | 运行时代码中本轮页面无 Max 资源引用和 AI 生成角色 |
| FR-12 | UI 更新不改变系统能力语义 | 现有 reducer、App Group writer、entitlement 和 Target 边界不变 |
| FR-13 | v0.6 不新增 Milo 动画资产 | 新增资产清单中无角色帧列、spritesheet、AI 补帧或新绘姿态；正式页面只引用现有 Approved 静态 PNG |

## 9. Non-functional requirements

### 9.1 Performance

- 品牌过渡不能延迟首个可用页面超过其自身必要渲染时间。
- 角色 PNG 应复用现有资产目录，避免重复打包同一大图。
- 长时间 Focus 页不运行角色逐帧动画或高频循环动效。

### 9.2 Accessibility

- 所有交互目标至少 44×44pt。
- Milo 装饰图默认不抢 VoiceOver；表达状态时提供简短 label。
- Timer、目标、真实保护状态和主 CTA 的 VoiceOver 顺序优先于角色描述。
- Dynamic Type 至 AXXXL 不遮挡主 CTA，不裁切关键状态。
- Reduce Motion 下不丢失信息、角色身份和操作。
- 主次与危险操作不可只靠颜色区分。

### 9.3 Privacy and security

- 不新增账号、网络、第三方 SDK 或云端数据。
- 不记录目标正文、所选 App 或权限敏感内容到 Beta 验证日志。
- 不新增 App Group key、writer 或 persistence schema，除非另行授权并完成架构门禁。

### 9.4 Compatibility

- 最低系统保持当前 iOS 17.0 目标。
- Simulator 只验 UI/流程候选；Shield、通知时机、Live Activity 和后台行为仍需真机证据。

## 10. State and navigation contract

本轮复用当前状态流，不增加平行状态机：

```text
系统 Launch Screen
→ Milo 品牌过渡（presentation-only）
→ onboarding / setup / recovery（由现有持久化状态决定）
→ setup
→ focusing
→ requestingAccess / accessWindow / focusing
→ completed
→ setup
```

- 品牌过渡只属于本地 presentation state。
- 恢复页、权限异常或不可解析数据的优先级高于品牌动画。
- 伙伴隐藏属于展示与可选范围，不自动授权宠物数据迁移。

## 11. Primary user flows

### Flow A：首次完成

`冷启动 → Milo 品牌过渡 → 选择 Milo → 输入目标/选择时长/完成必要授权 → 开始专注 → deadline 到达 → Milo 完成页 → 任务设置或记录`

### Flow B：离开并返回

`专注中 → 用户触发必要使用 → 申请/临时访问 → 返回 App → Milo Return → 请求恢复保护 → 继续倒计时 → 完成`

### Flow C：回访用户

`冷启动 → Milo 品牌过渡 → 直接进入当前恢复状态或任务设置 → 再次开始`

### Flow D：异常恢复

`冷启动 → 读取失败/授权撤销/跨进程状态不匹配 → Recovery/Permission 页面 → 用户修复 → 返回 setup`

品牌动画不得覆盖或伪装 Flow D。

## 12. Success metrics and V-S-C-R gates

本轮 UI 完成不等于产品成立。后续验证围绕同一人群、同一承诺和同一核心动作：

- **V（传播）**：多个独立内容实验是否重复触发“想和 Milo 一起专注”的明确兴趣；单条播放量不算成立。
- **S（可规模化）**：两周内可制作约 20 个只改变一个主要变量的内容实验；不依赖重新生产角色资产。
- **C（转化）**：看到内容或邀请后，真实安装并完成一次目标设置和专注；点赞、收藏或口头愿用不计入。
- **R（留存）**：无催促情况下，在自然周期内再次启动并完成第二次专注。

产品内候选指标：

1. 首次打开 → 选择 Milo 完成率。
2. 选择 Milo → 成功开始首次专注率。
3. 首次开始 → 完成一次专注率。
4. 发生离开 → 成功回到同一目标率。
5. 7 天内无催促二次完成率。
6. 崩溃、恢复失败、重复结算和关键流程中断率。

指标事件必须去标识化，且不能记录目标正文、所选 App 或账号信息。

## 13. Risks and dependencies

| Risk | State | Mitigation / gate |
| --- | --- | --- |
| 概念图角色与官方 PNG 不一致 | 已确认 | 正式运行时只用 Approved 资产；截图逐页核对 |
| Milo 单角色与历史 `.dog` 数据冲突 | 待确认 | 用户选择兼容策略；迁移前加测试 |
| 新视觉时长与现有业务时长不一致 | 待确认 | 默认沿用现有 30/45/60/120；修改需单独产品决策 |
| “暂停”在概念图出现但现有状态机语义可能不同 | 待确认 | 不凭 UI 新增状态；先映射现有必要使用/结束行为 |
| 启动动画拖慢或遮挡恢复 | 可控 | presentation-only、可提前结束、恢复优先、Reduce Motion |
| 新角色动画资产扩大范围 | 已阻断 | v0.6 明确禁止生产；后续增强另立门禁，不影响本版本发布 |
| 记录页展示不存在的数据 | 可控 | 只绑定现有 Store 字段；无数据则删 UI |
| Shield/Return 被视觉误报成功 | 高风险 | 继续使用请求/回执/设备证据分层措辞 |
| 历史 UI/DesignLab 脏改混入实现 | 高风险 | 开工前冻结精确基线和文件 allowlist；禁止顺手合并 |

## 14. Development boundaries

实现阶段默认允许的最小范围：

- 现有 FriendMVP SwiftUI 页面与其局部 presentation state。
- 现有 Design/Asset Catalog 中 Approved Milo 资源的引用关系。
- 与新 UI 直接相关的 CoreTests、Snapshot/fixture 和无障碍测试。

未经新授权禁止：

- 修改 reducer 状态语义、App Group key/writer、persistence schema。
- 修改 entitlement、签名、Target、最低版本、后台模式或第三方依赖。
- 删除 Max 资产或 `.dog` 兼容代码。
- 真机、TestFlight、上传、发布、账号和付费操作。

## 15. Release acceptance criteria

开发候选至少满足：

1. 六个核心页面和启动过渡均使用同一 UI 系统；只出现官方 Milo。
2. 运行时只使用现有 Approved Milo 静态姿态；无新增逐帧、spritesheet、AI 补帧或角色局部形变。
3. Max 在正式用户路径、VoiceOver 和运行时资源选择中不可见，但兼容数据未被破坏。
4. 主流程从 setup 到 focusing、return、completed 可完成，业务状态与当前 reducer 一致。
5. Debug/Release build 和相关 CoreTests 通过；Release 无可触发预览参数。
6. iOS 17 Simulator 完成 UI、Dynamic Type、Reduce Motion 和流程候选验收。
7. Shield、Return、Live Activity、通知和生命周期恢复按需要完成独立真机验证。
8. 用户对最终运行截图/录屏做视觉验收；概念图或 Preview 不替代。

## 16. Open questions — waiting for user approval

以下问题不阻止阅读 PRD，但在正式实现对应部分前必须确认：

1. **历史 Max 用户**：升级后是临时显示 Milo但保留 `.dog`，还是一次性迁移为 Milo？建议前者，避免不可逆数据迁移。
2. **专注时长**：沿用现有 30/45/60/120，还是改为概念图的 25/50/90？建议首轮沿用现有业务值。
3. **专注页“暂停”**：映射为现有必要使用流程、取消展示，还是新增真正暂停？建议不新增暂停状态，避免改变核心状态机。
4. **完成页主按钮**：使用“完成”返回任务设置，还是“再次一起专注”？建议“再次一起专注”，次级文字“先到这里”。
5. **启动动画频率**：每次冷启动，还是每天首次冷启动？建议每次进程冷启动播放，前后台切换不播放。
